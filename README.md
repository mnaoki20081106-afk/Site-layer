# Site-layer

サイト①とサイト②を重ねて表示するオーバーレイページと、両サイトのURL・重ね方を管理する管理画面を、Cloudflare Workers（Static Assets）+ KV で提供します。

## 仕組み（重要）

`/`・`/index.html` は、サイト①をiframeとして埋め込むのではなく、**Workerがサイト①のHTMLをまるごと取得し、このサイト自身のページとしてそのまま返します**（`<base>` タグでCSS/画像/リンクの相対パスをサイト①の実ドメインに向けています）。その中にサイト②を小さなiframeとして注入し、管理画面で指定した位置・サイズに重ねて表示します。

この方式にしている理由: サイト①をiframeとして埋め込むと、サイト①内のリンク（例: YouTubeアプリを開くようなアプリ連携リンク）は「入れ子になったフレーム」の中でのクリックになり、ブラウザ/OSがアプリ起動やユニバーサルリンクを正しく発動できないことがあります。サイト①を本物の最上位ページとして返すことで、サイト①内のリンクは通常のページ遷移として機能します。

トレードオフとして、サイト①自身がJSで `fetch()` するAPIなど相対パスに依存する動的な処理は、別ドメイン（このWorker）上で動くため正しく動作しないことがあります。静的なリンク・画像・CSSは `<base>` タグにより問題なく動作します。

## 構成

- `public/index.html` — フォールバック用の静的ページ。サイト①・サイト②のURLが未設定、またはサイト①への接続に失敗した場合のみ表示されます（通常時は `src/index.js` がサイト①を直接プロキシするため使われません）。
- `public/admin.html` — 管理画面。サイト①・サイト②のURLと、サイト②の重ね方（位置/サイズ/不透明度/クリック対象）を設定します。
- `src/index.js` — Cloudflare Worker本体。`/api/config` の GET（設定取得）・POST（設定更新、要トークン認証）を処理し、Cloudflare KV に保存します。`/` と `/index.html` はサイト①をプロキシしてサイト②を注入します（上記「仕組み」を参照）。それ以外のパスは `public/` 配下の静的ファイルをそのまま返します（Workers Static Assets）。
- `wrangler.toml` — Worker名、エントリポイント（`src/index.js`）、静的アセットのディレクトリ（`public`）、KVバインディングを設定。

## デプロイ手順（Cloudflareダッシュボード、ブラウザのみでOK）

このプロジェクトは Cloudflare の「Workers Builds」（GitHub連携で自動デプロイされるWorkers）を前提にしています。すでにダッシュボードでリポジトリを接続済みなら、mainブランチへのpush（このPRのマージなど）で自動的に再デプロイされます。

1. **KVネームスペースを作成**

   ダッシュボード「Workers & Pages」→ 上部タブ「KV」→「Create a namespace」→ 名前を `CONFIG_KV` として作成し、表示された namespace ID を控えます。

   `wrangler.toml` の `id = "REPLACE_WITH_KV_NAMESPACE_ID"` をそのIDに書き換えてコミットしてください（`preview_id` も同じIDで構いません）。

2. **KVをWorkerにバインド**

   対象のWorkerプロジェクトを開く →「Settings」→「Bindings」→「Add binding」→ KV namespace を選択
   - Variable name: `CONFIG_KV`
   - KV namespace: 手順1で作成したもの

3. **管理者トークンを設定**

   同じく「Settings」→「Variables and Secrets」→「Add」
   - Variable name: `ADMIN_TOKEN`
   - Value: 好きな長いランダム文字列（後で管理画面のログインに使うので必ずメモ）
   - Type: Secret（暗号化）

4. **再デプロイ**

   バインディングやシークレットの追加後は、mainブランチに新しいコミットをpushして新規デプロイを発生させてください（Cloudflareの「Retry deployment」は最初の接続時ビルドには使えないため）。

5. デプロイ後に発行されるURL（例: `https://site-layer.<subdomain>.workers.dev`、または独自ドメイン設定時はそのドメイン）で、以下にアクセスできます。

   - `/index.html` — オーバーレイ表示ページ（公開用）
   - `/admin.html` — 管理画面（URLを知っている人のみがアクセスする想定。必要であれば Cloudflare Access 等でさらにアクセス制限してください）

## 使い方

1. `admin.html` を開きます。`ADMIN_TOKEN` を環境変数として設定済みの場合、Workerがページ表示時に自動でトークンを埋め込むため、トークン入力欄は表示されず入力不要です（未設定の場合は入力欄が表示され、手入力したトークンはそのブラウザに記憶されます）。
2. サイト①・サイト②のURLを入力します。
3. サイト②の重ね方を、次のどちらかで設定します。
   - **ピクセル追従モード（推奨）**: 「サイト①内の重ねたい要素のCSSセレクタ」に、サイト①側のHTMLで重ねたい要素を指すセレクタ（例: `.ma .bo`）を入力し、「サイト②の元の高さ（px）」にサイト②のコンテンツ本来の高さを入力します。指定した要素の実際の位置・サイズにサイト②が自動で追従・拡縮し、スクロールやリサイズにも追従します。
   - **%指定モード**: セレクタを空欄にした場合、位置・サイズ（%）・不透明度・クリック対象を手動で指定する従来の方式になります。
4. 「保存」を押すと即座に `index.html` に反映されます。

## OGP（SNSでシェアしたときの見た目）

タイトル・画像は**サイト②（前面・重ねる側）**のOGPタグ（`og:title`/`og:image`、無ければ`twitter:title`/`twitter:image`）から取得して使います（サイト①ではありません）。ページ本体はサイト①のHTMLですが、`<title>`・`og:title`・`og:image`・`twitter:title`・`twitter:image` はサイト②の値で上書きします。`og:image`/`twitter:image` には、管理画面でサイト②のURLを実際に変更したタイミングのタイムスタンプを付与（`?_v=...`）するので、LINEやX（Twitter）などが画像を古いまま(キャッシュ)表示し続けることを防げます。`og:url` はこのサイト自身のURLに書き換えます。サイト②がOGPタグを持たない場合は、サイト①側の元のタグがそのまま使われます。

## サイト①内のリンクが押せない場合

**ピクセル追従モード**（CSSセレクタ指定）では、指定した要素自体のz-indexを引き上げてサイト②より前面に出すため、常にサイト①側の要素がクリックを受け取ります。

**%指定モード**を使っている場合は、サイト②（前面）の重ね範囲がサイト①の一部を覆っていると、その範囲内のクリックはサイト②が受け取り、サイト①側のリンクなどには届きません。範囲を、実際に重ねたい要素だけを覆う小さな範囲に絞ってください。範囲外は常にサイト①へのクリックがそのまま届きます。

## ディープリンク（アプリ連携リンク）が開かない場合

サイト①の中に「アプリを開く」系のリンク（YouTube・TikTokなど、`https://`以外のカスタムURLスキームや、署名付きのセッション連動トークンを使うタイプ）がある場合、正しく動作しないことがあります。理由は2つあります。

1. こちらのWorkerがサイト①のHTMLを取得するのは、実際にタップするユーザー本人のブラウザではないため、サイト側が「ページを取得したリクエスト」と「リンクを使おうとしたリクエスト」が別物だと判断し、不正アクセスとして拒否することがあります（TikTokの共有ページなどで確認済み）。
2. `https://`以外のカスタムURLスキーム（`アプリ名://...`など）は、ブラウザの仕様上、iframeや入れ子になったページの中からは開始できず、本当の意味での最上位ページからの操作でないと発動しません。

これらはヘッダーの調整などでは解決できない、ブラウザ・サイト側双方の意図的な仕様です。**ピクセル追従モード**（CSSセレクタ指定）を使っている場合は、「タップ時に本物のサイト①URLを新しいタブで開く」にチェックを入れてください。取得済みのHTMLに埋め込まれたリンクは使わず、タップした瞬間に**新しいタブ**で管理画面に設定したサイト①URLを直接開き直します。この新しいタブは、閲覧者本人のブラウザが直接・最上位で開くため、上記どちらの問題も回避できます（元のタブの重ね表示はそのまま残ります）。

## サイト①が正しく表示されない場合

- サイト①がBot対策（CAPTCHA、WAFなど）をしている場合、Worker からの取得がブロックされ、フォールバック画面が表示されることがあります。
- サイト①のJSが `fetch()` などで相対パスのAPIを呼んでいる場合、そのリクエスト先はこのWorkerのドメインになってしまうため、動的な機能が動かないことがあります（静的なリンク・画像・CSSは `<base>` タグにより正常に動作します）。
- サイト①がHTML以外（画像・PDFなど）を返す場合は、プロキシ・注入はせずそのまま中身を返します。

## 注意事項

- サイト①・サイト②側が `X-Frame-Options` や `Content-Security-Policy: frame-ancestors` で iframe 埋め込みを禁止している場合、そのサイトは重ね表示できません（相手サイトの設定に依存します）。
- 管理画面 (`admin.html`) はURLを知っていれば誰でも開けます。`ADMIN_TOKEN` をページに自動埋め込みする設定にすると、`admin.html` のソースを見れば誰でもトークンを読み取れる状態になり、実質「URLを知っている人なら誰でも設定変更できる」状態になります。自分専用・URLを他人に教えない前提での利用を想定した割り切りです。第三者に公開したくない場合は、Cloudflare Access などでページ自体へのアクセスも制限することを推奨します。

## トラブルシューティング

- ビルドログに `Executing user deploy command: npx wrangler deploy` と表示され `Could not detect a directory containing static files` で失敗する場合、プロジェクトが Pages ではなく Workers Builds として作成されています。その場合は `wrangler.toml` を Pages用（`pages_build_output_dir`）ではなく、Workers Static Assets用（`main` + `[assets]`）の形式にする必要があります（このリポジトリは対応済み）。
- KV バインディングや `ADMIN_TOKEN` を後から追加した場合、「Retry deployment」は使えません（`Cannot retry a build that was created with a seed_repo override` エラーになります）。設定変更後は、`main` ブランチに新しいコミットを push して新規デプロイ（Trigger: Push）を発生させてください。
- `ADMIN_TOKEN` をダッシュボードの「Variables and Secrets」に追加しただけでは、既存のデプロイには反映されません。追加後は必ず `main` に新しいコミットを push して再デプロイしてください。
- 再デプロイしても `/admin.html` のトークン入力欄が消えない場合は、`view-source:` を付けたURL（例: `view-source:https://<your-worker>.workers.dev/admin.html`）でHTMLソースを直接確認し、`window.__ADMIN_TOKEN__` を設定する `<script>` タグが実際に出力されているか確認してください。出力されていなければ Worker 側（`ADMIN_TOKEN` の保存や再デプロイ、または次項の `run_worker_first` 設定）の問題、出力されているのに欄が消えなければブラウザキャッシュの問題です。
- Workers Static Assets はデフォルトで、静的ファイルに一致するリクエスト（`/admin.html` など）を Worker のコードを経由せず直接返します。そのため `wrangler.toml` に `run_worker_first` を指定していないと、`ADMIN_TOKEN` 埋め込みやOGP書き換えのロジックが一度も実行されません（このリポジトリは `run_worker_first = true` を設定済みです。パスを配列で絞る書き方は環境によって反映されなかったため、すべてのリクエストで確実にWorkerを経由させる `true` にしています）。
